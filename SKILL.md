## 📋 Task Package Schema

Every task folder in `02_Task_Queue/` must contain:
1. `status.txt`: State machine token (`PENDING`, `IN_PROGRESS`, `REVIEW`, `DONE`, `ESCALATED`).
2. `role.md`: System prompt override for this specific task.
3. `recipe.md`: Step-by-step instructions and local Definition of Done (DoD).
4. `planning.md`: The micro-plan (BDD scenarios, compaction capsule).
5. `inputs/`: Input data or links to prior task outputs.
6. `output.md`: Primary deliverable generated by the worker.
7. `feedback.md`: Audit feedback written only by Checker or Human.
8. `action_log.jsonl` or `log.md`: Audit trail logging every tool execution.

## 🔧 Action Instructions for the Agent

### 0. How to Install or Update C.A.S.E. Skill

* **Local Project Install** (Workspace Skill):

* **To Update**: Navigate to the installed folder and run standard git pull:
  ```bash
  git pull
  ```

### 1. How to Bootstrap C.A.S.E. inside a project
If the user asks to "bootstrap", "deploy", or "initialize" C.A.S.E. scaffolding, run the cross-platform Python bootstrap script:
```bash
# Recommended (cross-platform and shell-agnostic):
python scripts/bootstrap.py .

# Alternatively (POSIX/Windows specific shells):
bash scripts/bootstrap.sh .
powershell scripts/bootstrap.ps1 .
```
This script will automatically generate the folders, templates, `MAP.md`, `CASE.md`, and configure gitignore.

### 2. How to Execute a Task in the Queue
If you are assigned to a task inside `02_Task_Queue/`:
1. **Transition**: Set `status.txt` to `IN_PROGRESS` using native file write APIs.
2. **Plan**: Write `planning.md` defining Given-When-Then test cases.
3. **Execute**: Modify files ONLY within the recipe boundaries. Log every tool call to `action_log.jsonl` (or write markdown bullets in `log.md` if using a weaker model).
4. **Self-Heal**: Run tests to verify changes. You have a **maximum of 3 consecutive self-healing attempts** to fix test failures before you must set state to `ESCALATED` and raise an issue.
5. **Submit**: Transition `status.txt` to `REVIEW` and wait for Checker review.

### 3. How to Verify/Audit a Task
If acting as a **Checker**:
1. Run the Node.js or Python verifier (whichever runtime is available) to check the task package integrity:
   ```bash
   # Node.js option:
   node verifiers/verify.js 02_Task_Queue/Task_<NNN>_<slug>

   # Python option:
   python verifiers/verify.py 02_Task_Queue/Task_<NNN>_<slug>
   ```
2. Inspect `output.md` against `recipe.md` DoD.
3. Approve by transitioning state to `DONE` (and perform a git commit), or reject by transitioning back to `PENDING` with feedback in `feedback.md`.

## 🌐 4. Cross-Platform & Cross-Shell Intelligent Adaptation Rules
Since C.A.S.E. is a declarative protocol, you (the AI Agent) are the primary executor. You MUST adapt to the host OS and shell intelligently:
- **Tool-First File Mutation**: Always use your native high-level file tools (e.g. `write_to_file`, `replace_file_content`) to change files like `status.txt`, `action_log.jsonl`, `planning.md`. **NEVER** run host shell redirection commands (e.g. `echo "IN_PROGRESS" > status.txt`) as they vary by shell and can pollute encodings (like UTF-16 in PowerShell).
- **Standard UTF-8 & LF**: All files written by you MUST use UTF-8 (without BOM) and LF (`\n`) line endings.
- **Dynamic Path Slashes**: Standardize command paths using forward slashes (`/`) even on Windows, as Node/Python and Windows file APIs natively support them.
